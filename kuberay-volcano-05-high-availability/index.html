前言

demo-job 正在运行，负责它的 Operator Pod 突然退出。已有的 Ray 计算可能继续执行，但谁来补 worker、回写作业状态、清理集群？如果退出的是 head Pod，答案又会不同。

第四篇已经解释了进程重启后怎样依靠已有资源继续协调。这篇把恢复分成三个层次：管理层由备用 Operator 接手资源协调；计算层由 Kubernetes、Ray 和应用各自恢复所负责的状态；服务层由 RayService 准备新集群并切换访问入口。下面沿这几个层次，说明各自需要哪些条件才能继续工作。

阅读基线为 KubeRay 6bf05eb17a3e、Ray 3f785c0711b9，依赖 controller-runtime v0.24.1、client-go v0.37.0。引用文件与基线一致；下文是源码分析和有条件的故障推演，没有集群实测数据。

Operator 的主备与接管

选主配置与副本部署

选主是在多个 Operator 实例中确定由谁负责协调资源；负责协调的实例称为主实例或 leader，其余实例等待接管。选主开关和实际部署几个副本来自不同配置。

ConfigMap 是 Kubernetes 用来保存配置数据的资源。若启用 configuration.enabled，chart 会把选主配置写进 ConfigMap；Operator 使用 --config 时忽略命令行配置，最终以挂载文件里的配置为准。配置模板与 main.go 中的配置加载分支共同决定最终值。

把副本分散到不同节点，可以让单个节点退出时仍有备用实例存活。部署升级还涉及 Deployment 的更新策略：此 chart 使用 Recreate，先终止旧版本 Pod，再创建新版本 Pod，所以升级期间会出现等待新实例启动的间隔。下面的接管流程以备用实例仍存活为前提。

Manager 是同一 Operator 进程中组织客户端、缓存和 Controller 的运行组件。RayCluster、RayJob 和 RayService 的 Controller 随所在 Manager 一起参与选主，由主实例统一启动协调。备用副本提供接管能力，协调并发仍由第三篇的配置控制。若关闭选主，每个实例都会独立协调自己观察到的对象，观察范围重叠时也会处理相同对象。

Lease 与选主范围

Lease 是 Kubernetes 保存租约状态的资源，包含持有者身份和续约信息。它可用于组件选主，具体抢占和续约逻辑由客户端执行。

controller-runtime 默认使用 coordination.k8s.io 的 Lease。ServiceAccount 是 Pod 内程序访问 Kubernetes API 时使用的身份。锁的命名空间未指定时，从 Pod 挂载的 ServiceAccount namespace 文件读取；集群外无法读取时需要显式配置。它与 watchNamespace 不同：前者决定锁放在哪里，后者决定观察哪些业务资源。

同一 Kubernetes 集群内，竞争相同 namespace/name 的实例属于同一组选主。这里需要同时看锁的范围和业务资源的观察范围：前者确定哪些实例互为主备，后者确定主实例接手哪些对象。两个安装若使用不同 namespace 中的锁，即使观察相同的 RayCluster，也会各自选出 leader；共用一把锁的实例则由一个主实例协调，并不按对象分片。更改锁命名空间时，还需要相应 Lease 权限；chart 默认在安装 namespace 创建的选主 Role，就是这组权限规则。

备用实例拥有自己的 Manager 和缓存。controller-runtime 先启动并同步缓存，再进入选主流程；获得领导权后启动需要选主的运行组件。下面是 OnStartedLeading 的连续节选：

新 leader 启动自己的 Controller，通过监听对象、执行协调接手工作。旧进程的 goroutine、调用栈和内存定时器都不会转移过来。如果切换恰好发生在请求已经发出、状态还没写回的时候，处理过程如图 2。

假设旧 leader 已成功创建 demo-job 的 submitter Kubernetes Job，也就是负责向 Ray 提交程序的 Job，随后在回写 RayJob 状态前退出。新 leader 读取这个 RayJob 资源对象和相关资源；createK8sJobIfNeed 按既定名称查询提交用 Job，查到后直接返回。若缓存尚未同步，创建同名对象可能返回 AlreadyExists，表示 API Server 中已有这个对象，下一轮再读取并判断。第四篇中保存的资源身份在这里继续发挥作用，让接管前后的实例围绕同一套资源推进流程。

接管过程中，还可能有旧 leader 已经发出、接收端正在处理的请求。Lease 决定哪个实例继续负责协调，已经被 API Server 或 Ray Dashboard 接收的操作则继续按各自流程处理，已经生效的结果也会保留。client-go 将从接收端拒绝旧 leader 操作的能力称为 fencing；这里的选主机制没有提供这层隔离。

失去领导权时，controller-runtime 的 OnStoppedLeading 将优雅停机等待设为零并返回 leader election lost；KubeRay 的 exitOnError 使进程退出。这是发送方停止协调的路径。接收端若要进一步辨认过期主实例，通常还需要校验请求中代表本次领导权的递增令牌，这条路径没有携带此类令牌。因此，理解切换时要分开看进程何时停止，以及已发出的请求何时完成。

这与第四篇的响应丢失场景相同：发送方超时，接收方可能已经完成操作，重试时需要识别已有结果。Kubernetes 用同名资源约束处理资源创建，业务数据库则需要自己的幂等键或事务。幂等键用来识别同一次业务操作；exactly-once 表示该操作的效果恰好生效一次，需要结果接收端参与实现。

接管时会根据已有资源重新建立进程内的安排。例如 RayService 把旧集群的待删除时间放在本地 map 中，即进程内的映射表。新实例观察到待清理集群后可以重新安排延迟，所以清理时刻可能比旧实例原先安排的晚一些。这段逻辑位于 cleanUpRayClusterInstance，延迟从新实例重新建立的安排继续计算。

控制面与 Ray 的恢复条件

Kubernetes 控制面失联

Operator 的选主和资源维护都要访问 API Server。主备同时失联时，Lease 续约和接管暂停，RayJob、Pod 等资源的查询与写入也受影响。etcd 是 Kubernetes 保存 API 对象的存储；如果中断来自这层存储，就需要先恢复控制面的依赖，Operator 副本才能继续工作。

已有 Ray 进程在节点和网络正常时可能继续执行，补建 Pod、扩容、调度新增资源和回写状态则需要控制面恢复。节点上的 kubelet 负责本机容器管理，控制面负责新 Pod 的创建和调度，两条路径承担不同工作。因而，某个 Operator 的 API 链路中断时，其他可访问 API 的实例仍可参与接管；所有实例都失联时，则要等待共同依赖恢复。

图 3 把这些依赖放在一起。GCS（Global Control Service）是 Ray 保存和管理集群元数据的服务，例如节点、actor 等信息。图中的 Redis 是可供 GCS 使用的外部键值存储服务，其恢复条件在下一节展开。API 调用和存储访问关系也限定了恢复范围：某个组件拥有备用实例，并不意味着它依赖的控制面与存储也同时可用。

worker、head 与 GCS 恢复

worker Pod 丢失后，KubeRay 根据仍有效的期望配置补足 Pod，Kubernetes 调度并启动容器。该节点上的 task、actor 能否恢复，则取决于 Ray 的重试、重启策略及状态来源。普通 task 的 max_retries 约束重试；actor 的 max_restarts 默认是零，即使允许重启，也需要应用恢复其内存状态。例如，程序可以把进度写入检查点，再由重启后的程序读取；检查点中保存哪些内容、怎样恢复，需要应用自己实现。

head 承载 GCS 等进程，恢复时既要重新启动容器，也要为这些进程提供可读取的状态。默认内存 GCS 的数据随进程丢失后，新的 head Pod 会重新建立运行环境，原集群元数据和 driver 的 Python 调用栈仍需要各自的恢复来源。第一篇的普通 demo-job 没有因此获得断点续跑能力。是否补建 head 还受配置控制：已标记为 provisioned（完成初始资源准备），且带 ray.io/disable-provisioned-head-restart 禁用标记的集群会跳过 head 重建，这个判断位于维护 Pod 的 reconcilePods 中。

这段代码给出了后端选择顺序：当 gcs_storage 使用默认的 memory 时，先检查 Redis 地址；有地址就选择 Redis 持久化后端，否则使用内存。GCS 重启后从选定的后端加载元数据，因此恢复需要 Redis 数据仍在、可访问，并沿用同一存储命名空间。

这里的“存储命名空间”用来区分不同 Ray 集群的后端数据，与 Kubernetes namespace 各有用途。KubeRay 的 Redis 容错配置函数 configureRedisFT 默认用 RayCluster UID 隔离数据。UID 是 Kubernetes 为每个资源对象分配的唯一标识：同一个 RayCluster 对象更换 head 时保留 UID，删除后再建同名对象会得到新的 UID。自定义 externalStorageNamespace 时，也需要为同时运行的不同集群分配各自的数据范围。

这个后端保存的是 GCS 元数据。Ray 对象、actor 内存和业务检查点有各自的保存方式，例如 actor 重启后可以读取应用检查点重建状态。Redis 自身能保留多少数据，则由它的可用性、落盘和复制策略决定。

数据保留还与 RayCluster 的生命周期关联。Redis 路径默认启用清理，Controller 会通过 finalizer 和清理 Job 删除对应存储命名空间的数据。这里的 finalizer 是删除前需完成清理的标记，清理 Job 执行后端数据删除。外部 Redis 为 GCS 重启保存恢复来源，集群删除时则按清理策略释放这部分数据。

GCS 恢复期间，存活 worker 上已有计算和对象可能继续可用，actor 创建、节点注册等依赖 GCS 的操作先暂停。KubeRay 在启用 GCS 容错且用户未覆盖时，把 worker 重连超时设为 600 秒，worker 在这段时间内等待恢复连接，超时则退出。head 上的其他进程也有各自的恢复过程。锁定版 GCS 文档将官方支持的 Redis 容错范围限定在 KubeRay 上的 Ray Serve；用于 RayJob 时，仍需按具体程序、运行进程和保存的状态分析恢复方式。

此源码还提供 backend: rocksdb 路径。RocksDB 是进程内使用的键值存储库，需要把数据文件放在可恢复的持久卷上，并限制为单个写入者。该路径属于 alpha 实验功能，要求开启默认关闭的 GCSFaultToleranceEmbeddedStorage，使用支持该后端的 Linux Ray 镜像。下文继续采用前述 Redis 场景。

RayService 的服务切换

这里换成一个持续提供 Ray Serve 服务的独立例子，对应第一篇资源关系图的右侧。RayService 与 demo-job 是两种使用方式；RayJob 完成后不会进入 RayService 的状态机。

Ray Serve 用来把应用部署为持续接受请求的服务，RayService 则管理承载它的 Ray 集群和应用部署。RayService 的 active 指当前集群，pending 指准备接替的集群。这里讨论传统的新集群蓝绿升级：保留当前集群的同时准备另一套集群，等它可用后再切换访问入口，不包括增量流量迁移。pending 的 Serve 应用非空且全部为 RUNNING 后，Controller 才把它选作切换目标；查询并判断应用状态的函数是 getAndCheckServeStatus。

旧集群存活、新集群有足够容量时，先准备再切换能减少服务空窗。Service 的变化还要传播到实际转发路径，在途长请求、已有连接和客户端重试会影响用户看到的切换过程。若 active 已故障而 pending 尚未就绪，则存在等待新服务准备好的间隔，已中断的请求需要客户端或应用处理。评估这种切换的效果，可以结合错误率、延迟和长连接行为观察；这条流程本身没有提供每个请求都无中断的保证。

小结：各层怎样配合恢复

下表是前述条件下的推演，不是故障注入结果；“可能继续”均以相关节点、网络和依赖仍正常为前提。

中断位置 谁来推进恢复 期间可能继续的工作 后续恢复条件
备用 Operator 退出 Kubernetes 补副本 leader 协调、Ray 计算 新副本启动后恢复备用能力
leader 退出，备用可访问 API Lease 选主、新 leader 协调 已有 Ray 计算 等待接管，并按资源身份确认在途操作的结果
主备均无法访问控制面 控制面或网络恢复后重建协调 部分已有计算与请求 控制面可访问后再推进新增 Pod、扩容和状态更新
worker 丢失 KubeRay 补 Pod，Ray 按策略恢复计算 其他健康 worker 的计算 task、actor 和对象恢复取决于策略与保存的状态
head 丢失，无 GCS 容错 按配置重建运行环境 原集群能否继续取决于剩余状态 元数据和应用进度各自需要恢复来源
head 丢失，Redis 容错条件满足 head 重建、GCS 加载、worker 重连 存活 worker 上已有计算或 Serve 副本 Redis 数据可读、重连在期限内完成；head 其他进程单独恢复
Redis 数据丢失或不可访问 存储系统恢复 取决于剩余状态与等待期限 后端实际保留并可读的数据决定 GCS 可恢复的进度
RayService 切换中失败 Controller 重试并重新观察资源 仍健康且可达的服务路径 逐步完成入口更新，结合客户端和应用处理受影响的请求

多副本让管理进程能够接管，外部存储为 GCS 提供可重新读取的元数据，应用检查点保存计算进度，RayService 则组织服务集群和入口的切换。这些机制按各自的范围配合：Operator 使用同一组选主与观察配置，GCS 沿用对应的存储身份，程序读取自己保存的状态，访问入口再跟随可用集群更新。高可用配置也需要围绕这些具体的恢复目标分别选择。

前五篇到这里完成了 KubeRay 管理与恢复流程的分析。第六篇开始增加 Volcano，继续追踪资源不足时 Pod 如何获得运行机会；调度器驱逐 Pod 后，计算恢复仍需遵守本篇说明的应用与 Ray 故障边界。
